# Upgrading a running installation

[🇷🇺 Русская версия](./UPGRADING_RU.md)

This page covers upgrading an installation that already serves users. For a fresh install follow the [README](../README.md) instead.

## Version matrix

| Chart version | `remnawave-panel` appVersion | `remnawave-subscription-page` appVersion |
| ------------- | ---------------------------- | ---------------------------------------- |
| `0.4.0`       | `3.4.4`                      | `8.0.0`                                  |
| `0.3.0`       | `3.2.1`                      | `8.0.0`                                  |
| `0.2.0`       | `2.7.4`                      | `7.2.1`                                  |

Both charts are released under a single tag, so their versions always move together even when only one of them changed.

## What the upgrade does to your data

The panel image runs `prisma migrate deploy` and `prisma db seed` from its entrypoint, before the application starts listening. There is no separate migration Job to run and nothing to trigger by hand — but it also means:

- the schema changes as soon as the new pod starts, not when you decide;
- a failed migration exits the container with code 1, so the pod crash-loops instead of serving a half-migrated schema;
- **migrations are not reversible.** Rolling the image tag back does not roll the schema back. The only rollback is restoring a database dump.

Because of this the panel deployment uses the `Recreate` strategy: the old revision is fully gone before the new one migrates. A startup probe gives the migration up to five minutes before the liveness probe is allowed to interfere.

## Before you start

1. **Dump the database.** This is the only rollback path.

   ```bash
   kubectl exec --namespace remnawave postgres-0 -- \
     pg_dump --username remnawave --format custom remnawave > remnawave-$(date +%F).dump
   ```

2. **Check the current chart and app versions** so you know which of the sections below applies:

   ```bash
   helm list --namespace remnawave
   ```

3. **Read the section for your starting point** and patch the Secret *before* upgrading the release. The panel validates its environment on startup and aborts on a missing required variable.

## Upgrading from chart 0.2.x (panel 2.7.4)

This is a major panel upgrade, `2.x` to `3.x`.

Panel `3.0.0` replaced the two JWT secrets with a single `APP_SECRET`. Add it to the existing Secret before upgrading, otherwise the panel will not start:

```bash
kubectl patch secret panel-secret \
  --namespace remnawave \
  --type merge \
  --patch "{\"stringData\":{\"APP_SECRET\":\"$(openssl rand -hex 64)\"}}"
```

The keys `JWT_AUTH_SECRET`, `JWT_API_TOKENS_SECRET`, `IS_DOCS_ENABLED`, `SCALAR_PATH`, `SWAGGER_PATH` and `CLOUDFLARE_TOKEN` are ignored by panel `3.x` and can be removed from the Secret.

Rotating the auth secret invalidates every panel session and every issued API token. The subscription page authenticates to the panel with such a token, so issue a new one and update `sub-page-secret` in the same maintenance window.

The subscription page moves from `7.2.1` to `8.0.0` in the same step; see the section below for what that changes.

## Upgrading from chart 0.3.x (panel 3.2.1)

No breaking changes in the panel itself: `3.2.2` through `3.4.4` add features and fixes, and the only new environment variables are optional.

`3.4.0` added the `SHORT_UUID_*` family, which controls how subscription link identifiers are generated. Leave it unset unless you have a reason not to — changing `SHORT_UUID_METHOD` on a running panel only affects identifiers issued afterwards, it does not rewrite existing subscription links.

What did change is the chart, and two of those changes are worth knowing about before you upgrade:

- the panel deployment switched from the default rolling update to `Recreate`, so the upgrade now has a short downtime window instead of overlapping pods;
- the readiness probe moved from `tcpSocket` to an HTTP check against `/api/health`, which pings Postgres. If you override `readinessProbe` in your values, replace the whole block rather than merging into it — Kubernetes rejects a probe that declares both `httpGet` and `tcpSocket`.

## What changed in subscription page 8.0.0

- `SUBSCRIPTION_UI_DISPLAY_RAW_KEYS` is gone. Page appearance is configured in the panel now, under subscription page configs.
- `SUBPAGE_CONFIG_UUID` selects which of those configs to serve. It defaults to the all-zero UUID, which is the config the panel seeds, so leave it unset unless you created your own.
- `INTERNAL_JWT_SECRET` is generated by the image entrypoint on every start. Do not put it in the Secret, and do not override the container command — the chart deliberately never does, because skipping the entrypoint leaves the variable unset and config validation aborts the container.

## Order of operations

1. Dump the database.
2. Patch `panel-secret` with anything the sections above require.
3. Upgrade `remnawave-panel`. Wait for the pod to become ready — the entrypoint logs `Migrations deployed successfully!` before the app starts.
4. Check that the nodes reconnect and pick up their configuration.
5. Issue a new API token if the panel secret was rotated, patch `sub-page-secret`, then upgrade `remnawave-subscription-page`.

```bash
helm upgrade remnawave-panel oci://ghcr.io/kroticw/remnawave-helm/remnawave-panel \
  --namespace remnawave \
  --version 0.4.0 \
  --reuse-values

kubectl rollout status deployment/remnawave-panel --namespace remnawave

helm upgrade remnawave-subscription-page oci://ghcr.io/kroticw/remnawave-helm/remnawave-subscription-page \
  --namespace remnawave \
  --version 0.4.0 \
  --reuse-values
```

## Rollback

`helm rollback` restores the manifests, not the database. After a panel upgrade has run its migrations, rolling the release back gives you an old panel against a new schema, which is a worse state than the one you were trying to leave.

- **The panel failed to start and the migration did not complete** (the entrypoint logged a migration failure): `helm rollback remnawave-panel --namespace remnawave` is enough.
- **The migration completed and the panel misbehaves afterwards**: restore the dump first, then roll the release back.

  ```bash
  helm rollback remnawave-panel --namespace remnawave
  kubectl exec --stdin --namespace remnawave postgres-0 -- \
    pg_restore --username remnawave --clean --if-exists --dbname remnawave < remnawave-YYYY-MM-DD.dump
  ```

- **The subscription page** holds no state of its own, so `helm rollback remnawave-subscription-page --namespace remnawave` is always safe.

## After the upgrade

```bash
kubectl get pods --namespace remnawave
kubectl logs deployment/remnawave-panel --namespace remnawave --tail 50
helm list --namespace remnawave
```

Check in the panel UI that the nodes are online, then open a subscription link and confirm the page renders and the client config downloads.
