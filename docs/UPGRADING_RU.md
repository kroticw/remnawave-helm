# Обновление работающей установки

[🇬🇧 English version](./UPGRADING.md)

Страница о том, как обновить установку, которая уже обслуживает пользователей. Для установки с нуля смотрите [README](../README_RU.md).

## Соответствие версий

| Версия чарта | appVersion `remnawave-panel` | appVersion `remnawave-subscription-page` |
| ------------ | ---------------------------- | ---------------------------------------- |
| `0.5.1`      | `3.4.4`                      | `8.0.0`                                  |
| `0.5.0`      | `3.4.4`                      | `8.0.0`                                  |
| `0.4.0`      | `3.4.4`                      | `8.0.0`                                  |
| `0.3.0`      | `3.2.1`                      | `8.0.0`                                  |
| `0.2.0`      | `2.7.4`                      | `7.2.1`                                  |

Оба чарта публикуются под одним тегом, поэтому их версии всегда идут вместе, даже если изменился только один из них.

## Что обновление делает с данными

Образ панели запускает `prisma migrate deploy` и `prisma db seed` из энтрипойнта, до того как приложение начнёт слушать порт. Отдельный Job для миграций не нужен, запускать руками нечего — но из этого следует:

- схема меняется в момент старта нового пода, а не когда вы решите;
- неудачная миграция завершает контейнер с кодом 1, поэтому под уходит в crash-loop, а не обслуживает наполовину мигрированную схему;
- **миграции необратимы.** Откат тега образа не откатывает схему. Единственный откат — восстановление дампа базы.

Поэтому деплоймент панели использует стратегию `Recreate`: старая ревизия полностью исчезает до того, как новая начнёт мигрировать. Startup-проба даёт миграции до пяти минут, прежде чем в дело вмешается liveness.

## Перед началом

1. **Снимите дамп базы.** Это единственный путь отката.

   ```bash
   kubectl exec --namespace remnawave postgres-0 -- \
     pg_dump --username remnawave --format custom remnawave > remnawave-$(date +%F).dump
   ```

2. **Посмотрите текущие версии чарта и приложения**, чтобы понять, какой раздел ниже вам нужен:

   ```bash
   helm list --namespace remnawave
   ```

3. **Прочитайте раздел про свою точку старта** и поправьте Secret *до* обновления релиза. Панель проверяет переменные окружения при старте и падает на отсутствующей обязательной.

## Обновление с чарта 0.2.x (панель 2.7.4)

Это мажорное обновление панели, `2.x` → `3.x`.

Панель `3.0.0` заменила два JWT-секрета одним `APP_SECRET`. Добавьте его в существующий Secret до обновления, иначе панель не стартует:

```bash
kubectl patch secret panel-secret \
  --namespace remnawave \
  --type merge \
  --patch "{\"stringData\":{\"APP_SECRET\":\"$(openssl rand -hex 64)\"}}"
```

Ключи `JWT_AUTH_SECRET`, `JWT_API_TOKENS_SECRET`, `IS_DOCS_ENABLED`, `SCALAR_PATH`, `SWAGGER_PATH` и `CLOUDFLARE_TOKEN` панель `3.x` игнорирует, их можно удалить из Secret.

Смена секрета аутентификации инвалидирует все сессии панели и все выданные API-токены. Страница подписки ходит в панель именно с таким токеном, поэтому выпустите новый и обновите `sub-page-secret` в то же окно работ.

Страница подписки на этом же шаге переходит с `7.2.1` на `8.0.0` — что при этом меняется, смотрите в разделе ниже.

## Обновление с чарта 0.3.x (панель 3.2.1)

Ломающих изменений в самой панели нет: с `3.2.2` по `3.4.4` идут новые возможности и исправления, а все новые переменные окружения опциональные.

В `3.4.0` появилось семейство `SHORT_UUID_*`, которое управляет генерацией идентификаторов ссылок на подписку. Не трогайте его без нужды: смена `SHORT_UUID_METHOD` на работающей панели влияет только на идентификаторы, выданные после неё, и не переписывает уже существующие ссылки.

Что действительно изменилось — это чарт, и о двух изменениях стоит знать до обновления:

- деплоймент панели перешёл с обычного rolling update на `Recreate`, поэтому теперь у обновления есть короткое окно недоступности вместо пересечения подов;
- чарты `0.4.0` и `0.5.0` перевели readiness-пробу на HTTP-запрос к `/api/health`. Такая проба не проходит никогда: в панели `3.4.4` этого адреса нет, а её проверка прокси обрывает любой запрос, пришедший не через обратный прокси по HTTPS. Пропустите обе версии и обновляйтесь сразу до `0.5.1`, где проба снова на `tcpSocket` — см. следующий раздел.

## Обновление до чарта 0.5.1

Образы не меняются. `0.5.1` чинит readiness-пробу панели: она снова на `tcpSocket`, как startup- и liveness-пробы. С `0.4.0` и `0.5.0` под панели стартует, прогоняет миграции и так и не становится готовым: HTTP-проба к `/api/health` всегда заканчивается EOF — в панели `3.4.4` такого адреса нет, а её `ProxyCheckMiddleware` пишет в лог `Reverse proxy and HTTPS are required.` и обрывает каждый прямой запрос.

Если вы переопределяете пробы в своих values, учтите: Helm не заменяет чартовый блок вашим, а сливает их. Чтобы сменить вид пробы, обнулите чартовый в том же переопределении, иначе в спецификации пода окажутся два обработчика и API-сервер её отвергнет:

```yaml
readinessProbe:
  tcpSocket: null
  httpGet:
    path: /your/path
    port: http
```

### Выход из релиза, застрявшего на 0.4.0 или 0.5.0

Если обновление до `0.4.0` или `0.5.0` упало, потому что под так и не стал готовым, обновление до `0.5.1` тоже упадёт — с ошибкой `readinessProbe.tcpSocket: Forbidden: may not specify more than 1 handler type`. Helm строит патч от последнего *успешного* релиза, где уже был `tcpSocket`, поэтому патч не убирает `httpGet`, оставленный упавшим релизом на живом Deployment. Сначала замените пробу на живом объекте, потом обновляйтесь:

```bash
kubectl patch deployment remnawave-panel \
  --namespace remnawave \
  --type json \
  --patch '[{"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe","value":{"tcpSocket":{"port":"http"},"periodSeconds":10,"failureThreshold":3}}]'
```

Миграции упавшего обновления к этому моменту уже применены, поэтому не откатывайтесь на `0.3.x` без восстановления дампа базы — см. [Откат](#откат).

## Обновление с чарта 0.4.x

Образы не меняются. В `0.5.0` добавлен только `pathFilter` у `remnawave-subscription-page`, и по умолчанию он выключен — то есть обновление ничего не меняет, пока вы сами его не включите.

Включайте, если сканирующий трафик по хосту подписки виден у вас как пятисотые на ingress. Приложение обрывает TCP-соединение на каждый запрос, который не ведёт к существующей подписке, — оно никогда не отвечает 404, — а прокси перед ним показывает это как 502. Поэтому фоновое сканирование интернета по `/.env`, `/.git/config` и `/docs/phpinfo.php` читается как всплеск серверных ошибок вашего собственного ingress.

```yaml
pathFilter:
  enabled: true
```

С ним до подов доезжают только `/assets/…`, `/<shortUuid>` и `/<shortUuid>/<clientType>`, а всё остальное получает 404 от прокси. Обе ветки маршрутизации закрыты: Ingress переходит на regex-пути с `nginx.ingress.kubernetes.io/use-regex`, HTTPRoute — на совпадения типа `RegularExpression`.

Перед включением сверьте шаблон со своей установкой. По умолчанию он рассчитан на обычные ссылки подписки; `CUSTOM_SUB_PREFIX`, нестандартный `SHORT_UUID_METHOD` или `SHORT_UUID_CUSTOM_PATTERN` в панели, а также legacy-ссылки Marzban дают ссылки другой формы, и фильтр, который о них не знает, ответит 404 живым пользователям. Под свою форму правьте `pathFilter.shortUuidPattern` и `pathFilter.clientTypes`.

Это сужение проблемы, а не её закрытие: запрос к несуществующему, но правильному по форме идентификатору подписки по-прежнему доезжает до приложения и по-прежнему заканчивается 502. Починить это до конца может только приложение — ответив 404 вместо обрыва соединения.

## Что изменилось в странице подписки 8.0.0

- `SUBSCRIPTION_UI_DISPLAY_RAW_KEYS` больше нет. Внешний вид страницы настраивается теперь в панели, в конфигурациях страницы подписки.
- `SUBPAGE_CONFIG_UUID` выбирает, какую из этих конфигураций отдавать. По умолчанию это нулевой UUID — та конфигурация, которую панель создаёт сама, так что не задавайте переменную, если не завели свою.
- `INTERNAL_JWT_SECRET` генерируется энтрипойнтом образа при каждом старте. Не кладите его в Secret и не переопределяйте команду контейнера — чарт сознательно этого не делает: в обход энтрипойнта переменная останется пустой, и проверка конфигурации завершит контейнер.

## Порядок действий

1. Снять дамп базы.
2. Поправить `panel-secret` тем, что требуют разделы выше.
3. Обновить `remnawave-panel`. Дождаться готовности пода — энтрипойнт пишет `Migrations deployed successfully!` до старта приложения.
4. Проверить, что ноды переподключились и забрали конфигурацию.
5. Если секрет панели менялся — выпустить новый API-токен, поправить `sub-page-secret`, затем обновить `remnawave-subscription-page`.

```bash
helm upgrade remnawave-panel oci://ghcr.io/kroticw/remnawave-helm/remnawave-panel \
  --namespace remnawave \
  --version 0.5.1 \
  --reuse-values

kubectl rollout status deployment/remnawave-panel --namespace remnawave

helm upgrade remnawave-subscription-page oci://ghcr.io/kroticw/remnawave-helm/remnawave-subscription-page \
  --namespace remnawave \
  --version 0.5.1 \
  --reuse-values
```

## Откат

`helm rollback` возвращает манифесты, но не базу. После того как обновление панели прогнало миграции, откат релиза даёт старую панель поверх новой схемы — состояние хуже того, из которого вы уходили.

- **Панель не стартовала и миграция не прошла** (энтрипойнт написал про сбой миграции): достаточно `helm rollback remnawave-panel --namespace remnawave`.
- **Миграция прошла, но панель ведёт себя неправильно**: сначала восстановите дамп, затем откатывайте релиз.

  ```bash
  helm rollback remnawave-panel --namespace remnawave
  kubectl exec --stdin --namespace remnawave postgres-0 -- \
    pg_restore --username remnawave --clean --if-exists --dbname remnawave < remnawave-YYYY-MM-DD.dump
  ```

- **Страница подписки** своего состояния не держит, поэтому `helm rollback remnawave-subscription-page --namespace remnawave` безопасен всегда.

## После обновления

```bash
kubectl get pods --namespace remnawave
kubectl logs deployment/remnawave-panel --namespace remnawave --tail 50
helm list --namespace remnawave
```

Проверьте в интерфейсе панели, что ноды онлайн, затем откройте ссылку на подписку и убедитесь, что страница рендерится и конфигурация клиента скачивается.
